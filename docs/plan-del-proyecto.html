Gauss-Jordan paso a paso

Les comparto el plan de la aplicación web educativa que propongo para capturar sistemas lineales de 2 × 2 a 5 × 5, resolverlos con Gauss-Jordan exacto y enseñar cada operación entre filas hasta la forma escalonada reducida.

Cómo leer este documento. Lo escribí para que podamos compartirlo tal como está. Aquí explico qué quiero construir, cómo propongo repartir el trabajo y qué debemos dejar listo antes de empezar a programar.

Producto

Qué propongo que haga la web

Etapa 1 · Tamaño. Quiero que podamos elegir 2 × 2, 3 × 3, 4 × 4 o 5 × 5 mediante tarjetas con la matriz de ejemplo y una explicación del recorrido.

Etapa 2 · Datos. Quiero capturar coeficientes y términos independientes con ecuaciones legibles, matriz aumentada [A | b], carga de ejemplo, limpieza y validación de enteros, decimales y fracciones.

Etapa 3 · Procedimiento. Quiero mostrar la lista de operaciones, el paso actual, el cálculo, la matriz Antes, la matriz Después, la fila modificada y la vista completa de todas las matrices.

Etapa 4 · Resultado. Quiero presentar solución única, infinitas soluciones o sin solución, junto con la forma reducida, la comprobación de ecuaciones y las acciones para volver, descargar o resolver otro sistema.

Regla visual. Mantendremos el stepper de Tamaño, Datos, Procedimiento y Resultado en todas las pantallas. La pantalla activa usará morado y los pasos completados usarán verde.
Estados obligatorios. Diseñaremos estados de carga, error de validación, error del servidor, matriz vacía, solución única, infinitas soluciones y contradicción.
Decisión de alcance. En el MVP no guardaremos sistemas ni crearemos cuentas porque el prototipo no muestra persistencia. El backend será stateless; agregaremos Sanctum si el catedrático exige usuarios o historial.

Contrato de datos

La respuesta que vamos a compartir

Voy a usar classification como discriminador. Todos los campos del sobre existirán siempre; solo cambiarán los valores permitidos según la clasificación.

Entrada del solver

{
  "size": 3,
  "matrix": [
    ["1", "1", "1", "6"],
    ["2", "3", "1", "11"],
    ["1", "2", "3", "14"]
  ]
}

Los valores viajan como texto racional. Se aceptan enteros, decimales, negativos y fracciones como 1/3. La matriz siempre tiene size filas y size + 1 columnas.

Salida de solución única

{
  "classification": "unique",
  "solution": {"a":"1","b":"2","c":"3"},
  "free_variables": [],
  "parameters": {},
  "contradiction": null,
  "verification": [
    {"equation":1,"left":"6","right":"6","ok":true},
    {"equation":2,"left":"11","right":"11","ok":true},
    {"equation":3,"left":"14","right":"14","ok":true}
  ]
}

Además incluye initial_matrix, steps y rref completos, como en el ejemplo detallado del plan.

Regla de presentación. El frontend decide el texto y color según classification. No intenta deducir la clasificación mirando ceros ni recalcula matrices. Si falta un campo obligatorio del sobre, se trata como error de contrato.

Descarga PDF

Cómo propongo manejar la descarga de pasos (PDF)

Backend

  • Ruta: POST /api/gauss-jordan/steps.pdf. Jacob es el responsable de implementarla y explicarla; Diego revisa que reutilice el solver.
  • Recibe exactamente el mismo JSON que /solve.
  • Reutiliza GaussJordanService; no mantiene una segunda implementación.
  • Genera un PDF con la matriz inicial, cada operación, matrices Antes/Después, forma reducida, clasificación y solución o contradicción.
  • Responde 200 con Content-Type: application/pdf y Content-Disposition: attachment; filename="gauss-jordan-3x3-pasos.pdf".
  • Responde 422 con el mismo formato de errores JSON si la entrada es inválida.

Frontend

  • El botón vive en ResultPage y se muestra cuando existe una respuesta válida.
  • api.js envía el payload y recibe un Blob.
  • Se crea un enlace temporal con URL.createObjectURL, se descarga y se revoca la URL.
  • Durante la descarga el botón se deshabilita y muestra estado de carga.
  • Si falla, se conserva el resultado en pantalla y se muestra un mensaje con reintento.
  • El nombre usa el tamaño del sistema; no contiene datos privados porque el MVP no guarda historial.
Criterio de aceptación. El PDF debe abrirse, contener todos los pasos en el mismo orden del JSON y no cortar matrices, fracciones, encabezados ni la fila de contradicción. Se prueba al menos con 2 × 2, 5 × 5, fracciones, infinitas e inconsistente.

Normas del equipo

Reglas que propongo para Git y las revisiones

Git y PRs

  • Ramas: main para entrega, develop para integración y feature/<nombre>-<modulo> para trabajo.
  • Commits claros: feat(solver): registra operación de intercambio.
  • Nadie hace push directo a main o develop; todo entra por PR.
  • Cada PR incluye pruebas, captura o evidencia y archivos modificados.
  • Tablero: Por hacer → En progreso → Revisión → Hecho.

Reglas de código

  • El algoritmo vive en el servicio; los componentes no contienen fórmulas de eliminación.
  • La validación de API vive en Form Requests.
  • El estado del solver tiene una sola fuente.
  • Los valores racionales se mantienen como texto exacto hasta la presentación.
  • Los nombres de campos del contrato no cambian sin actualizar backend, frontend y documentación.
  • Se verifica build y pruebas antes de cerrar cada sprint.
